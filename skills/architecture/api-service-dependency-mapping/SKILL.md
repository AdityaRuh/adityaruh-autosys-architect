# api-service-dependency-mapping

## When to Use

Use this skill when the user provides project context and wants to understand service boundaries, API relationships, dependency direction, or integration coupling.

## Procedure

1. Review the provided repository structure, service definitions, API context, and documented integrations.
2. Identify the main services, APIs, upstream dependencies, downstream consumers, and shared infrastructure touchpoints.
3. Describe dependency direction and call out central chokepoints, circular coupling, or brittle integration paths.
4. Summarize the dependency map in concise CLI-friendly language and add a Mermaid diagram when it improves clarity.
5. Distinguish observed dependencies from inferred recommendations.
6. Keep the process read-only and limited to approved context.

## Pitfalls

- Do not assert dependencies that are not visible in the provided context.
- Do not mistake naming similarity for actual runtime coupling.
- Do not expand into implementation refactoring unless it helps explain the architecture impact.

## Verification

The skill succeeds when it returns an accurate dependency map summary, including notable bottlenecks or coupling risks, based on the provided project context.
