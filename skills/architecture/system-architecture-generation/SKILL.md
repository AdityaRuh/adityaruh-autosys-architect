# system-architecture-generation

## When to Use

Use this skill when the user asks for a new system architecture, wants a production-ready design recommendation, or needs help choosing between monolith, microservices, event-driven, or serverless shapes. Use it only for read-only analysis and recommendation work in the CLI workflow.

## Procedure

1. Confirm the available inputs: product description, core requirements, scale expectations, reliability needs, budget sensitivity, preferred stack, and any optional project context.
2. If key constraints are missing, stop and ask focused follow-up questions before finalizing a recommendation.
3. Choose the simplest architecture that can realistically satisfy the confirmed requirements while preserving a staged path for future growth.
4. Produce a recommendation that names the major components, their responsibilities, data flow, and why the chosen shape fits the current maturity and constraints.
5. Include a Mermaid diagram when the architecture would be easier to understand visually.
6. State tradeoffs explicitly, including operational complexity, likely bottlenecks, reliability implications, and rough cost posture.
7. Keep the recommendation cloud-neutral by default unless the user explicitly requests a specific provider.
8. Do not propose autonomous deployment, provisioning, destructive actions, unrestricted shell execution, or secret-handling workflows.

## Pitfalls

- Do not over-engineer early-stage systems when a simpler architecture is sufficient.
- Do not present rough cost or scale guidance as a guarantee.
- Do not assume repository context exists when the user has not provided it.
- Do not recommend direct production modifications or write-capable integrations by default.

## Verification

The skill succeeds when the user receives a concrete architecture recommendation with a clear component breakdown, a rationale tied to confirmed constraints, and a Mermaid diagram when relevant.
