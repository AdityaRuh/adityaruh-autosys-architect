# architecture-adaptation-when-constraints-change

## When to Use

Use this skill when a returning user reports changed requirements, growth, budget pressure, reliability targets, or other confirmed constraints that require revising a previously approved architecture.

## Procedure

1. Restate the prior approved architecture context and the newly changed constraints.
2. Identify which parts of the existing design still fit and which assumptions are no longer valid.
3. Recommend the smallest viable set of architecture changes needed to satisfy the updated constraints.
4. Explain what should change now, what can wait, and what tradeoffs the new direction introduces.
5. Revisit scaling, reliability, cost, dependency boundaries, and stack implications only where the changed constraints affect them.
6. Keep the updated recommendation cloud-neutral by default unless the user explicitly requests otherwise.
7. Stay within read-only advisory scope and avoid deployment, provisioning, or destructive actions.

## Pitfalls

- Do not discard prior approved decisions without explaining why the new constraints invalidate them.
- Do not overcorrect into a far more complex architecture than the updated requirements justify.
- Do not assume unchanged budget or reliability posture if the user has explicitly revised it.

## Verification

The skill succeeds when it delivers an updated architecture plan that clearly links each recommendation change to a confirmed change in constraints.
