# scalability-optimization-suggestions

## When to Use

Use this skill when the user asks how to scale an existing design, expects traffic growth, or needs staged evolution guidance after bottlenecks or stricter reliability targets appear.

## Procedure

1. Review the confirmed current architecture, expected traffic pattern, known bottlenecks, and reliability targets.
2. Identify the most likely near-term scaling constraints across compute, storage, database access, background work, network boundaries, and dependency contention.
3. Recommend phased improvements in order: changes to make now, changes to defer until thresholds are met, and changes that are unnecessary for the current stage.
4. Explain how each scaling step affects complexity, cost, and operational load.
5. Keep the plan practical and incremental rather than jumping directly to a distributed design.
6. Include checkpoints that signal when the next stage is justified.
7. Stay within read-only recommendation scope and avoid autonomous operational changes.

## Pitfalls

- Do not recommend premature decomposition.
- Do not ignore cost and team-operability tradeoffs while optimizing for scale.
- Do not present speculative thresholds as guarantees unless the user has supplied supporting context.

## Verification

The skill succeeds when it delivers a phased scaling plan with immediate, later, and unnecessary-for-now recommendations tied to confirmed constraints.
