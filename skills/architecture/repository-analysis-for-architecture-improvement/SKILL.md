# repository-analysis-for-architecture-improvement

## When to Use

Use this skill when the user provides repository context and wants architecture improvement findings, coupling analysis, boundary suggestions, or risk notes derived from the current project structure.

## Procedure

1. Inspect only the approved repository context the user has provided.
2. Identify major components, service boundaries, layering patterns, dependency hotspots, and cross-cutting concerns.
3. Call out tight coupling, unclear boundaries, risky shared state, or structure that may block scaling, reliability, or maintainability.
4. Recommend practical architecture improvements that can be adopted incrementally.
5. Distinguish observed repository facts from higher-confidence recommendations and from optional future improvements.
6. Keep all analysis read-only and avoid destructive or write-capable actions.
7. If repository context is insufficient, say so directly instead of inferring hidden structure.

## Pitfalls

- Do not claim repository findings without evidence in the provided context.
- Do not assume GitHub access or local files are available if they were not provided.
- Do not turn code-structure observations into speculative operational claims.

## Verification

The skill succeeds when it returns repository-backed findings with coupling or risk notes and a practical set of architecture improvement recommendations.
