# infrastructure-recommendation-engine

## When to Use

Use this skill when the user asks for infrastructure guidance, wants a deployment shape recommendation, or needs help aligning hosting and runtime choices with budget, maturity, and reliability needs.

## Procedure

1. Gather the confirmed architecture context, budget sensitivity, maturity stage, reliability goals, and any explicit provider preferences.
2. Recommend infrastructure that fits the current stage with the lowest practical operational burden.
3. Explain the major choices such as compute model, data stores, networking boundaries, observability expectations, and scaling approach.
4. Prefer cloud-neutral guidance by default and note where a provider-specific implementation could fit if later requested.
5. Include rough cost posture and reliability notes for each recommended layer.
6. Respect the confirmed Docker-sandbox backend assumption and CLI-focused operating model where relevant.
7. Do not recommend autonomous provisioning or deployment execution.

## Pitfalls

- Do not jump to multi-service or multi-region complexity without confirmed need.
- Do not imply provider lock-in is required unless explicitly requested.
- Do not include destructive or write-capable operational actions.

## Verification

The skill succeeds when it returns an infrastructure recommendation that matches confirmed maturity, budget, and reliability constraints and explains why the chosen operating model is appropriate.
